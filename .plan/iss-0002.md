# ISS-0002 — Reject Unmanaged Files That Occupy Renderer-Owned Names

## 1. Outcome

Bring projection inventory into agreement with the authoritative issues specification:

> Unmanaged matching files cause the render to fail before any write or deletion.

A direct regular child whose name belongs to the active renderer but whose content is not owned must become a preflight conflict, whether or not that filename appears in the expected projection.

The command must identify the conflicting path, return the existing operational-failure exit code `1`, and leave the complete output directory unchanged.

## 2. Current behavior and root cause

`projection.Plan.inventory` handles expected and nonexpected files through different branches:

1. An unmanaged expected target fails at once.
2. A nonexpected child with a managed name is read.
3. When that child's content is unmanaged, inventory silently continues.

The third step implements the detailed v0 handoff but contradicts `docs/objects/issues.md` §8. The projection test `TestBuildPlanIgnoresUnownedStrays` currently encodes the contradictory behavior.

Issue #1 also added `TestApplyPreservesEmbeddedMarkerTextInUnmanagedFile`. After this fix, that matching file must still be preserved, but preservation happens by rejecting the plan before `Apply`, not by successfully applying around the conflict.

## 3. Behavioral decision

Use the renderer's managed-name predicate as a reserved flat namespace:

| Existing direct child | Expected? | Name owned? | Content owned? | Behavior |
| --- | --- | --- | --- | --- |
| Regular file | Yes | Yes | Yes | Compare and update when different. |
| Regular file | Yes | Yes | No | Fail before mutation. |
| Regular file | No | Yes | Yes | Plan stale removal. |
| Regular file | No | Yes | No | Fail before mutation. |
| Regular file | No | No | Either | Ignore. |
| Directory | No | Either | N/A | Ignore. |
| Symlink | No | Either | N/A | Ignore without following. |
| Non-regular special file | No | Either | N/A | Ignore. |

This preserves user files outside the renderer namespace while preventing ambiguous ownership inside it. No new flag or overwrite escape hatch is introduced.

## 4. Implementation changes

### 4.1 — Reject the conflict during inventory

Edit `internal/projection/writer.go`:

1. Keep the existing expected-target preflight unchanged.
2. During direct-child inventory, continue ignoring non-owned names, directories, symlinks, and other non-regular entries.
3. Read each nonexpected regular child whose name is owned.
4. Return an error when its content is unmanaged instead of continuing.
5. Include the concrete conflicting path in the error.
6. Continue planning removal only when both name and content are owned.

The check remains inside `BuildPlan`, before `Plan.Apply` and before the application branches into normal, dry-run, or check mode. All three modes therefore receive the same safety behavior without mode-specific code.

### 4.2 — Split the contradictory projection test

Edit `tests/projection/projection_test.go`:

1. Replace `TestBuildPlanIgnoresUnownedStrays` with a focused test that rejects an unmanaged regular file carrying a managed name.
2. Assert the error identifies the conflicting filename.
3. Assert no expected file was created and the conflicting bytes remain unchanged.
4. Retain a separate test proving that unrelated regular files, matching directories, matching symlinks, and their pointees remain untouched.

### 4.3 — Reconcile the issue #1 filesystem regression

Edit `tests/projection/writer_test.go`:

1. Rename the embedded-marker regression to describe preflight rejection.
2. Expect `BuildPlan` to fail because the matching file is unmanaged.
3. Assert the file's original bytes survive.
4. Assert no expected index file is written.

The predicate-level cases in `tests/issues/render_test.go` remain unchanged and continue proving that embedded marker text does not grant ownership.

### 4.4 — Reconcile documentation

Edit `.plan/v0-implementation.md` so its nonexpected-child matrix matches the authoritative object specification:

- managed name plus managed regular content → remove;
- managed name plus unmanaged regular content → fail;
- unmanaged name → ignore;
- directory or symlink → ignore.

Replace the test requirement “stale unmanaged file preservation” with explicit coverage for unmanaged matching-file rejection and unrelated-file preservation.

Clarify the reserved-name conflict in `README.md` under the safety model. Do not change `docs/objects/issues.md`; it already states the intended behavior.

Add the fix to the next patch section in `CHANGELOG.md`.

## 6. Verification

Automated gates:

```bash
gofmt -w internal/projection/writer.go tests/projection/projection_test.go tests/projection/writer_test.go
go test -race ./...
go vet ./...
go build ./...
git diff --check
```

Behavioral checks:

1. An unmanaged `iss-9999.md` makes normal mode fail without creating or changing any file.
2. The same conflict makes `--dry-run` and `--check` fail without mutation.
3. An unmanaged `notes.md` remains ignored.
4. A matching directory remains ignored.
5. A matching symlink remains ignored and its pointee is never read or changed.
6. A managed stale issue file is still reported and removed normally.
7. A second self-render is byte-identical and `gh render issues --check` succeeds.

## 7. Non-goals

- Do not add `--force`, adoption, or overwrite behavior.
- Do not change ownership-marker semantics from issue #1.
- Do not make projection application transactional; issue #3 owns write-time revalidation.
- Do not reserve filenames that fail the active renderer's managed-name predicate.

## 8. Definition of done

Issue #2 is complete when production behavior, tests, the detailed implementation handoff, README, and authoritative specification all agree; every mode fails before mutation on an unmanaged renderer-pattern file; unrelated filesystem entries remain untouched; the full validation suite passes; issue #2 is closed; and the refreshed `.issues/` projection is committed.
