# gh-render v0 Implementation Plan

> v0 delivers a safe `gh render issues` command, proves it against Terrazzo, publishes `v0.1.0`, and removes Terrazzo's repository-local issue-rendering script.

## 1. Context

Terrazzo currently uses `scripts/sync-github-issues.mjs` to generate `.issues/`. The behavior is generic, but keeping the implementation in each repository duplicates tooling and assumes that repository's runtime.

The public `digimata/gh-render` repository already contains a precompiled Go extension scaffold and release workflow. The approved behavior is defined in `docs/spec.md` and `docs/objects/issues.md`.

## 2. Scope

v0 includes:

- `gh render issues`;
- current-repository and explicit `--repo` resolution;
- complete paginated issue retrieval;
- normalized issue records;
- deterministic issue and index Markdown;
- managed-file protection;
- atomic per-file replacement;
- safe stale-file deletion;
- `--check` and `--dry-run`;
- unit, golden, filesystem, and CLI tests;
- a `v0.1.0` release;
- Terrazzo migration.

v0 excludes comments, reactions, project fields, other GitHub objects, bidirectional updates, configuration files, templates, and pluggable output formats.

## 3. Implementation sequence

### 3.1 — CLI boundary

1. Parse the `issues` object and its four flags.
2. Reject unknown flags and incompatible validation modes.
3. Preserve the documented exit-code contract.

### 3.2 — GitHub source

1. Resolve the current or explicit repository through the authenticated GitHub CLI context.
2. Fetch issues with pagination.
3. Exclude pull requests.
4. Normalize API records before rendering.

### 3.3 — Deterministic renderer

1. Render issue frontmatter, heading, source link, and body.
2. Render the collection index.
3. Sort every record and collection field explicitly.
4. Add golden fixtures for escaping, Unicode, empty fields, and closed issues.

### 3.4 — Filesystem writer

1. Compute the complete expected projection.
2. Inventory managed, unmanaged, and stale paths.
3. Reject conflicts before writing.
4. Replace files atomically.
5. Remove only stale managed issue files.

### 3.5 — Validation modes

1. Make `--dry-run` report the write plan without mutation.
2. Make `--check` distinguish current and stale projections.
3. Test that neither mode changes contents or modification times.

### 3.6 — Live acceptance

1. Render `digimata/terrazzo` into a temporary output directory.
2. Compare the temporary projection with the existing legacy projection.
3. Review every proposed content or schema difference.
4. Render into the temporary directory twice and confirm the second pass is clean.
5. Exercise authentication, network, conflict, and stale-file failures.

## 5. Verification

Automated:

```bash
go test ./...
go vet ./...
go build -o gh-render .
```

Required behavioral checks:

1. Root and object help return successfully.
2. Invalid usage returns `2`.
3. API and filesystem failures return `1`.
4. A current `--check` returns `0`.
5. A stale `--check` returns `3`.
6. A dry run leaves contents and modification times unchanged.
7. An unmanaged target prevents all mutations.
8. Repeated rendering is byte-identical.
9. Pull requests are excluded from mixed API fixtures.
10. Terrazzo's seven issues render correctly.

## 6. Release and migration

1. Update `CHANGELOG.md` from `Unreleased` to `0.1.0`.
2. Commit the validated implementation.
3. Tag and push `v0.1.0`.
4. Confirm the release workflow publishes the expected macOS binaries.
5. Install with `gh extension install digimata/gh-render`.
6. Render Terrazzo into a temporary directory and compare it with the legacy projection.
7. Remove Terrazzo's Node renderer, `pnpm issues:pull`, and the verified legacy-generated `.issues/` files.
8. Regenerate Terrazzo's `.issues/` through the installed extension.
9. Run `gh render issues --check` in Terrazzo.
10. Confirm Terrazzo's second render and repository checks are clean.
