# gh-render v0 Implementation Plan

> v0 delivers a safe `gh render issues` command, proves it against Terrazzo, publishes `v0.1.0`, and removes Terrazzo's repository-local issue-rendering script.

The coding handoff with concrete types, signatures, package boundaries, and test cases is [v0-implementation.md](v0-implementation.md).

## 1. Context

Terrazzo currently uses `scripts/sync-github-issues.mjs` to generate `.issues/`. The behavior is generic, but keeping the implementation in each repository duplicates tooling and assumes that repository's runtime.

The public `digimata/gh-render` repository already contains a precompiled Go extension scaffold and release workflow. The approved behavior is defined in `docs/spec.md` and `docs/objects/issues.md`.

## 2. Scope

v0 includes:

- `gh render issues`;
- current-repository and explicit `--repo` resolution;
- complete paginated issue retrieval;
- normalized issue records;
- state, label, assignee, and author selectors;
- deterministic ranking and result limits;
- self-describing filtered projections;
- deterministic issue and index Markdown;
- managed-file protection;
- atomic per-file replacement;
- safe stale-file deletion;
- `--check` and `--dry-run`;
- unit, golden, filesystem, and CLI tests;
- a `v0.1.0` release;
- Terrazzo migration.

v0 excludes comments, reactions, project fields, other GitHub objects, bidirectional updates, configuration files, templates, and pluggable output formats.

## 3. Implementation sequence

### 3.1 — CLI boundary

1. Parse the `issues` object, common flags, selectors, ranking, and limit.
2. Reject unknown flags and incompatible validation modes.
3. Reject invalid states, sort fields, orders, and nonpositive limits.
4. Preserve the documented exit-code contract.

### 3.2 — GitHub source

1. Resolve the current or explicit repository through the authenticated GitHub CLI context.
2. Fetch issues with pagination.
3. Exclude pull requests.
4. Normalize API records before rendering.

### 3.3 — Selection

1. Resolve `@me` to the authenticated GitHub login.
2. Apply state, repeated-label, assignee, and author selectors with the documented AND semantics.
3. Rank matches by the selected field and order, with issue number as the deterministic tie-breaker.
4. Apply the limit after ranking.
5. Sort selected records by ascending issue number for serialization.

### 3.4 — Deterministic renderer

1. Render issue frontmatter, heading, source link, and body.
2. Render the collection index.
3. Record the concrete normalized selection in the index.
4. Sort every record and collection field explicitly.
5. Add golden fixtures for escaping, Unicode, empty fields, closed issues, and filtered projections.

### 3.5 — Filesystem writer

1. Compute the complete expected projection.
2. Inventory managed, unmanaged, and stale paths.
3. Reject conflicts before writing.
4. Replace files atomically.
5. Remove only stale managed issue files.

### 3.6 — Validation modes

1. Make `--dry-run` report the write plan without mutation.
2. Make `--check` distinguish current and stale projections.
3. Test that neither mode changes contents or modification times.

### 3.7 — Live acceptance

1. Render `digimata/terrazzo` into a temporary output directory.
2. Compare the temporary projection with the existing legacy projection.
3. Review every proposed content or schema difference.
4. Render into the temporary directory twice and confirm the second pass is clean.
5. Render the top three most recently updated issues.
6. Render issues matching a label and the authenticated assignee.
7. Exercise authentication, network, conflict, and stale-file failures.

## 4. Files touched

| File | Action |
| --- | --- |
| `main.go` | Edit process entry point. |
| `main_test.go` | Delete after moving its cases into `tests/`. |
| `internal/app/app.go` | Create dispatch and exit mapping. |

| `internal/issues/client.go` | Create fetch and normalization. |
| `internal/issues/model.go` | Create normalized issue model. |
| `internal/issues/select.go` | Create filtering, ranking, and limiting. |
| `internal/issues/render.go` | Create Markdown projection. |
| `internal/projection/projection.go` | Create plan and change types. |
| `internal/projection/writer.go` | Create safe filesystem writer. |
| `tests/app/app_test.go` | Create CLI behavior tests. |
| `tests/issues/` | Create client, selection, and rendering tests. |
| `tests/issues/testdata/` | Create golden fixtures. |
| `tests/projection/` | Create projection and filesystem safety tests. |
| `README.md` | Edit implemented usage. |
| `CHANGELOG.md` | Add the `v0.1.0` entry. |

`internal/app` owns command parsing and orchestration. `internal/issues` owns the complete object-specific pipeline: fetch, normalize, select, and render. `internal/projection` owns generic write planning and filesystem safety that future object renderers can reuse. All tests and fixtures live under `tests/`.

Go enforces `internal/` visibility, preventing external modules from importing application implementation as a public API while allowing this repository's black-box test packages to import it. A second object renderer may justify extracting shared GitHub transport later; v0 does not create a package for that hypothetical reuse.

## 5. Verification

Automated:

```bash
go test ./...
go vet ./...
go build -o gh-render .
```

Required behavioral checks:

1. Root and object help return successfully.
2. Invalid usage returns `2`.
3. API and filesystem failures return `1`.
4. A current `--check` returns `0`.
5. A stale `--check` returns `3`.
6. A dry run leaves contents and modification times unchanged.
7. An unmanaged target prevents all mutations.
8. Repeated rendering is byte-identical.
9. Pull requests are excluded from mixed API fixtures.
10. Selector types combine with AND and repeated labels require every label.
11. `@me` resolves to the authenticated login and is recorded concretely.
12. Ranking ties resolve deterministically before the limit is applied.
13. Filtered projections remove only managed files outside the selected set.
14. Terrazzo's full and filtered projections render correctly.

## 6. Release and migration

1. Update `CHANGELOG.md` from `Unreleased` to `0.1.0`.
2. Commit the validated implementation.
3. Tag and push `v0.1.0`.
4. Confirm the release workflow publishes the expected macOS binaries.
5. Install with `gh extension install digimata/gh-render`.
6. Render Terrazzo into a temporary directory and compare it with the legacy projection.
7. Remove Terrazzo's Node renderer, `pnpm issues:pull`, and the verified legacy-generated `.issues/` files.
8. Regenerate Terrazzo's `.issues/` through the installed extension.
9. Run `gh render issues --check` in Terrazzo.
10. Confirm Terrazzo's second render and repository checks are clean.
